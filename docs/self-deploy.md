# The board Worker deploys itself from a signed main (#C968)

The design is Security's (the note `c968-credential-design.md`, in the owner's shared folder); the owner chose one Cloudflare account (B, #T1837) and the change itself on #T1779. This file says what the code does and what the owner sets up once, in the Cloudflare dashboard. Nothing here has been run against the live dashboard: **the lead checks each dashboard click below against the live page before posting it** (Cloudflare's dashboard changes).

## What the code does
Cloudflare's own Git build (Workers Builds) runs on every push to `main`. Its build command is, in this order:

```
[ "$(sha256sum scripts/self-deploy-gate.mjs | cut -c1-64)" = <the gate's sha256, typed by the owner> ] && node scripts/self-deploy-gate.mjs && node scripts/self-deploy-run.mjs
```

1. **The hash check** runs first and lives only in the dashboard. A commit to `main` cannot weaken the gate: changing `scripts/self-deploy-gate.mjs` means the owner updates one hash in the dashboard (the build fails closed until then).
2. **`scripts/self-deploy-gate.mjs`** refuses (the build fails, nothing deployed, the reasons printed) unless: the build's commit is `main`'s tip; it carries a Security note starting `SECURE` and a Checker note starting `PASS` (git notes belong to the commit, so they name that exact sha), and so does every commit between the Worker's current `BUILD_SHA` and it (`main` can be pushed to directly), unless, per role, a signed commit of the range has that role's note saying `line from <sha>` (as the release tool writes it, on the first line) with a base that is an ancestor of it and not before the Worker's current `BUILD_SHA`, and the commit is on that line (so a fixing commit signed on the line covers the commit landed under it; see the group section below); the build is not told to install dependencies (`SKIP_DEPENDENCY_INSTALL`); and the Worker's current `BUILD_SHA` (read from Cloudflare with the build's token) is an ancestor of it (forward only, like the pairs). A `BUILD_SHA` it cannot read refuses: a first deploy stays the owner's, by a pair. When the commit is the one already deployed it says so and exits 0.
3. **`scripts/self-deploy-run.mjs`** runs only behind the gate's marker (`.self-deploy-ok`, ignored by git), and does what the owner's pair does: builds the store page from the build variable `BOARD_CONFIG_JSON` (written to a temporary folder outside the repository), applies the D1 migrations, and deploys with `--var BUILD_SHA:<commit>`. Wrangler is pinned. It never prints the token, the account or the config.
4. **The Worker tells the owner's phone** `board deployed <7-character sha>` once per deployed commit (`worker/push-rules.mjs`, from its own `BUILD_SHA`, through the phone push of #C904): a deploy he did not start is seen within minutes.

## What the owner sets up once (an install ask, not a chat line)
1. **Connect the Worker to the repository** in the dashboard (Workers & Pages, the board Worker, Settings, Builds): the Cloudflare GitHub app on `aponsin/flight-board` only, production branch `main` only, **preview builds off**.
2. **The deploy token.** Do NOT let Workers Builds create one (it carries Workers Routes: Edit on every zone, KV and R2). Make a custom user token under My Profile, API Tokens, for the board's account only: Account, Workers Scripts: Edit; Account, D1: Edit; Account, Account Settings: Read; **no zone permission, no KV, no R2**; an end date about six months out; no client IP filter (Cloudflare publishes no build IP ranges). Choose it in the build settings as an existing token. It can still replace any Worker and read or change any D1 database on that account (one-account trade-off, accepted on #T1837).
3. **Build variables and secrets:** **`SKIP_DEPENDENCY_INSTALL=1`** first (Security F1: Workers Builds installs dependencies before the build command, so a `preinstall` or `prepare` script on `main` would run ahead of the pinned gate; the gate refuses unless this is `1` or `true`), then `BOARD_CONFIG_JSON` (the board config, as one line of JSON; make it a secret if any of it is), and make sure the build sees `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`. **Check live whether build secrets reach the build command as well as the deploy command**: the gate and the run script need them in the build command.
4. **The build command** is the line above, with the gate's sha256 typed in (`sha256sum scripts/self-deploy-gate.mjs` on a checkout of the signed commit; the lead posts it). **The deploy command must be changed** from the default `npx wrangler deploy` to a no-op such as `true`, so the build's own deploy cannot bypass the gate. Check live that the field accepts it.
5. **Cut-over, after the first self-deploy works:** delete `board.private.json` and run `npx wrangler logout` on the Mac, so no deploy-capable credential is left where agents work. Rollback then moves to the dashboard (Deployments, roll back), which the owner does himself; the pairs' rollback line stops working and the pair files stop being needed.

## A carried sign-off does not count here (#C1026)
The release tool (`scripts/board-release.mjs`) can land a plain re-cut of a signed commit without new notes: a single commit on `origin/main` whose message, changed paths, modes and blobs equal the signed commit's, whose files no landing in between touched, and which changes only `tests/`, `docs/`, `CHANGELOG.d/` or `page/` (never `worker/`, `hooks/`, `gate/`, `collector/`, `keeper/`, `scripts/`, `wrangler*`, `package*.json`, `.github/` or a dotfile; `page/` only when the landings touched nothing under `page/` or `worker/`), after the full suite is green on that tip. It prints `carried: self-deploy will refuse until signed`: **`scripts/self-deploy-gate.mjs` was not taught the carry.** The gate still wants a real Checker PASS and Security SECURE on every commit it deploys, so a landing carried this way waits for the reviewers to sign it before a Worker deploy covers it.

## A group's line notes count here too (#C1032, #C1045)
The release tool reads, for every commit of `origin/main..tip`, a note of its own or the role's line note on the tip (a first line `PASS ... line from <40-hex base>` in `refs/notes/checker`, `SECURE ... line from <40-hex base>` in `refs/notes/security`; each role independently, base an ancestor of `origin/main` and of the tip and where the tip's line left main, no merge commit, 30 commits at most), and it refuses a commit with a note of its own that is not PASS/SECURE even under a line note. Since #C1045 the gate reads a sign-off the same way, per role, from the same functions: `ROLE_WORD`, `roleLineBase`, `GROUP_MAX` and `roleUnsigned` live in `scripts/self-deploy-gate.mjs` (the file the dashboard hash pins) and `scripts/board-release.mjs` imports them. In the gate, a role's line note on any signed commit of the Worker's range covers base..that commit for that role when the base is an ancestor of it and not before the Worker's current `BUILD_SHA`, with no merge commit and at most 30 commits; one role's line never signs for the other. The one difference: the release tool's "where the tip's line left main" cannot be read after the landing (the build commit is main's tip), so the gate's bound is "not before what is deployed", as before. **This changed the gate's sha256:** the owner types the new hash in the dashboard at the cut-over (the build fails closed until then).

## What this changes in trust (said once)
Today a deploy needs the owner to run a pair whose hashes Security signs out of band. After this it needs a push to `main` plus two notes, and agents can push both, so a confused or rogue agent could deploy unreviewed Worker code. It still cannot read the token. The phone push is how the owner would notice.
