- 2026-11-16: Each card writes its "Changes" line to its own file, `docs/DATA.d/<card id>.md`, and a fold step joins them into this file (#C1090). On 11-16 every card appended its dated line at the end of `docs/DATA.md`, so each landing conflicted every waiting branch there (#C1075 was rebased and re-signed twice, for #C1081 and #C1083, and three more rebases followed the same day). The same cure as `CHANGELOG.d/` (#C1019): `scripts/data-fragments.mjs` (`--check`, `--write`, or no flag to print the result) reads `docs/DATA.d/*.md` (each file one line, `- YYYY-MM-DD: ...`, named for a card id; `README.md` and dotfiles skipped), orders the lines oldest date first, then by the first `#C<number>` in the line (lowest first), then by file name, and appends them after the last line of this file; `--write` also deletes the files. Nothing follows a symbolic link: a link, or a folder where a file belongs, is named and refused, as `changelog.mjs` does. The existing lines stay where they are. The fold is a card, not a commit the landing job makes: the Worker's self-deploy gate (`scripts/self-deploy-gate.mjs`, hash-pinned) wants a Checker PASS and a Security SECURE on every commit it would deploy, and the job cannot sign. So a fold card (a Board-Id starting `fold-data-fragments`) runs `--write` on a branch and is signed Quick like any card. `scripts/board-land.mjs` (the landing job; pinned, so it rides the next owner pack) reads what each tip changes in docs/DATA.md against main (`git diff -U0 --no-renames main...tip -- docs/DATA.md`, three dots: the line's own change, not main's) and REFUSES a tip that ADDS a dated line (`+- YYYY-MM-DD: `) there unless every card it carries is a fold card (an edit of a row or a principle still lands: Checker 2's F1 on v3, which refused every edit; a diff that could not be read makes the tip wait, never counts as no change); the git arguments and the two counts are pure helpers (`dataDiffArgs`, `addedDatedLines`, `fragmentListArgs`, `fragmentCount`), tested, one against a real temporary repository; and it counts `docs/DATA.d/<card id>.md` on origin/main (lower-case card files only: the README is not one) and, at 5 or more (`FOLD_DUE`), logs `FOLD DUE: N DATA fragments wait ...` and writes `dataFragments` and `foldDue` in `land-report.json`, which Release and Manager read with the run's other lines. The store's dispatch (`collector/store-dispatch.mjs`, `foldDueCheck`) reads that report too (`landingFrom` now returns `foldDue`, true only for a fresh report that says so with a count) and wakes an idle Boardsmith once per MT day with a card of its own, `fold-due-<yyyy-mm-dd>` (step `folddue`, whose line text is in `gate/reset.mjs` `DISPATCH_STEPS`: "FOLD DUE: 5 or more DATA fragments wait in docs/DATA.d on main; cut the fold card ..."); `dispatch-state.json` keeps `fold` { date, wokenAt, done }, which is done once Boardsmith has worked after the wake and is dropped when the report stops saying foldDue, so a later due wakes again. Both are pinned files and ride the next owner pack. No migration, table or column; `scripts/board-release.mjs` is not changed. Tests: `tests/data-fragments.test.mjs` (two branches that each add a fragment merge with no conflict, and the fold writes both lines in date order) `tests/landing-refuses-data-md-edit.test.mjs` and `tests/fold-due-wakes-boardsmith.test.mjs`.
